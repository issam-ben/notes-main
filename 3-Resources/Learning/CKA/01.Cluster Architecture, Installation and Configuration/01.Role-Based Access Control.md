Accessing resources in Kubernetes is allowed only for authenticated users, every user has read-only access, only the Admin has full privileges, allowing normal user to have admin permissions is a grave security risk, and for user to send a request to the admin every time they need to change something is a tedious process, so that's where RBAC Role-Based Access Control comes to the rescue.

> [!Definition]
> RBAC is a set of policies for users, groups, and processes, by allowing or disallowing access to manage API resources.

So RBAC helps us to give certain users the permissions they need. it can be used in a variety of use cases.
RBAC consists of three building blocks:
- Subject: users, processes, groups, ServiceAccounts that requires an access. 
- Resource: The k8s api resource e.g. Deployment, node,pods,...etc
- Operation (verb): the action that cab be executed on the resource e.g. Creating a pod, deleting a service...etc.


## Creating a Subject
User account, Groups or ServiceAccount can be used as a subject.
- Users and Groups: 
	- Not stored in etcd.
	- Not represented as an API resource 
	- Meant for processes running outside the cluster.
- ServiceAccounts: 
	- Exist as objects in Kubernetes.
	- Meant for processes running inside the cluster. 
### User accounts and groups
- The kubernetes cluster administrator is the one supposed to manage (create, give permissions, delete,...) user acounts.
- The admin then, distributes the credentials of the account to the real person or be used by an external process.
- Calls to the API server with a user needs to be authenticated, k8s offers a variety of authentication methods, shown on table below:

| **Authentication method** | Description                                                           |
| ------------------------- | --------------------------------------------------------------------- |
| X.509 client certificate  | Uses an OpenSSL client certificate to authenticate                    |
| Basic authentication      | Uses username and password to authenticate                            |
| Bearer tokens             | Uses OpenID (a flavor of OAuth2) or webhooks as a way to authenticate |
#### Steps of Creating a user using OpenSSL:
1. Login to K8s control plane (Master Node)
2. Create a temp Dir
	1. `$ mkdir cert && cd cert`
3. Create a Private Key using OpenSSL
```bash
openssl genrsa -out johndoe.key 2048
```
4. Create a Certificate Sign Request (CSR), with file extension `.csr` 
```bash
openssl req -new -key johndoe.key -out johndoe.csr -subj \
"/CN=johndoe/O=cka-study-guide"
```

	1.-subj \"/CN= /O=: -subj provides the username (CN) and the group (O).

5.  Sign the CSR with the Kubernetes cluster certificate authority (CA)
	1. CA can usually be found on the directory `/etc/kubernetes/pki`
	2. Needs to contain ca.crt and ca.key files.
	3. Using minikube which stores those files in the directory pass `[<code>~/.minikube</code>`
```
openssl x509 -req -in johndoe.csr -CA /.minikube/ca.crt -CAkey \
/.minikube/ca.key -CAcreateserial -out johndoe.crt -days 364
```
6. Create the user in Kubernetes by setting a user entry in kubeconfig for johndoe.Point to the CRT and key file. Set a context entry in kubeconfig for johndoe

```
 kubectl config set-credentials johndoe \
--client-certificate=johndoe.crt --client-key=johndoe.key
```

```
kubectl config set-context johndoe-context --cluster=minikube \
--user=johndoe
```
7. To switch to the user use the context named `johndoe-context`
```
kubectl config use-context johndoe-context
```
8. check the current context.
```
kubectl config current-context
```

### ServiceAccounts
A Service Account is an account that is used by non-humans. Some service applications need to interact with the Kubernetes cluster, unlike normal users who interact with the cluster using ==kubectl== executable or K8s dashboard, ServiceAccounts interact with kubernetes by sending requests to the API server via ==RESTful http== calls.

> [!example] 
> Helm charts use ServiceAccount to authenticate the service process.

* ServiceAccounts exist as ServiceAccount objects in the API server.
* ServiceAccounts are bound to Kubernetes namespaces, every namespace gets a ==default== ServiceAccount upon creation.
* ServiceAccounts are represented in the API server, unlike useraccounts which are treated by the api server as opaque data not API objects.
* ServiceAccounts are portable...

#### Default Service Accounts
Upon cluster creation, Kubernetes automatically creates a ServiceAccount object name default, for every namespace in the cluster.
It gets the [default API discovery permissions](https://kubernetes.io/docs/reference/access-authn-authz/rbac/#default-roles-and-role-bindings) only, by default.
If a deployed pod doesn't get manually assigned a ServiceAccount, Kubernetes will assign the default ServiceAccount to the pod.
#### Use cases
* When your pods need to communicate with the API server, for ex: read-only access to sensitive info stored in secrets, or granting [cross-namespace access](https://kubernetes.io/docs/concepts/security/service-accounts/#cross-namespace).
* Pods need to communicate with external services, for ex: a pod uses cloud identity management.
* authenticate to image registry.
* External services such as CI/CD pipelines.
* Third party security software inside the cluster.
#### Using ServiceAccounts

##### Creating ServiceAccounts
* Imperative:
	* kubectl create serviceaccount sa-name
* Declarative:
```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: sa-name
```
##### Listing ServiceAccounts
To list available ServiceAccounts in the cluster, we use kubectl get command like this:
```shell
kubectl get serviceaccounts
```

##### ServiceAccount Details
To see details about the ServiceAccount like the secret token name, use describe option with kubectl
```shell
kubectl describe serviceaccount sa-name
```
##### Assigning a ServiceAccount to a Pod
```shell
kubectl run build-observer --image=alpine --restart=Never --serviceaccount=sa-name
```
As an alternative way, use declarative commands to assign a Pod to a ServiceAccount in the Pod's YAML file.
